# Policy front door (nginx)

Pexip Infinity allows **one external policy server per system location**. The
Mattermost integration and the AD avatar lookup are both external policy
servers, but they answer *different request types*:

| Request type | Path Pexip appends to the profile URL | Served by |
| --- | --- | --- |
| Service configuration | `/policy/v1/service/configuration` | Mattermost plugin |
| Participant avatar | `/policy/v1/participant/avatar/<alias>` | ad_policy |

This container routes each path to the right backend, so a single policy
profile can point at it and both integrations work.

```
Pexip nodes ──► proxy (this) ──┬─► https://<mattermost>/plugins/com.pexip.pexip-app/api/policy/v1/service/configuration
                               └─► http://ad_policy:5000/policy/v1/participant/avatar/<alias>
```

## Configuration (environment variables)

| Variable | Required | Meaning |
| --- | --- | --- |
| `MATTERMOST_POLICY_URL` | yes | The plugin's policy base URL, exactly as the Pexip docs give it: `https://<mattermost>/plugins/com.pexip.pexip-app/api/` |
| `POLICY_USER`, `POLICY_PASSWORD` | yes | The username/password **generated by the Mattermost plugin**. Pexip sends one credential for every request type, so the proxy enforces the same one on the avatar path. |
| `AVATAR_UPSTREAM_URL` | no | Where avatar requests go. Default `http://ad_policy:5000` (the compose service). |
| `TLS_MODE` | no | `self-signed` (generate a certificate on first start, using `PROXY_HOSTNAME`), `provided` (use mounted `fullchain.pem`/`privkey.pem`, refuse to start without them), `off` (HTTP only), or `auto` (default: HTTPS if a certificate is mounted). |
| `PROXY_HOSTNAME` | with self-signed | Name or IP that goes into the generated certificate. |
| `DNS_RESOLVER` | no | Resolver for the upstream hostnames. Defaults to the container's own. |

Certificates live in `/etc/nginx/certs` (`fullchain.pem`, `privkey.pem`); the
compose file mounts `certs/proxy/` there read-write so a generated certificate
survives restarts. A self-signed certificate must be uploaded to Pexip under
**Certificates > Trusted CA certificates**; `./setup.sh cert` prints it. For a
certificate from your own CA use `./setup.sh csr` and `./setup.sh install-cert`
(see INSTALL.md).

## Run with Docker Compose (customer deployment)

`./setup.sh` asks for everything below and writes `.env`; see INSTALL.md.
By hand, add to `.env` alongside the LDAP settings:

```
MATTERMOST_POLICY_URL=https://mattermost.example.com/plugins/com.pexip.pexip-app/api/
POLICY_USER=<from the Mattermost plugin settings>
POLICY_PASSWORD=<from the Mattermost plugin settings>
TLS_MODE=self-signed
PROXY_HOSTNAME=policy.example.com
```

Then:

```
docker compose up -d --build
./setup.sh check
```

## Pexip configuration

Create **two** policy profiles with the same URL and credentials; only the
enabled request types differ.

| Profile | URL | Credentials | Enabled request types | Assign to |
| --- | --- | --- | --- | --- |
| Mattermost + AD avatars | `https://<proxy>/` | Mattermost plugin user/password | service configuration, participant avatar | the Mattermost system location |
| AD avatars only | `https://<proxy>/` | same | participant avatar | every other location that should show AD photos |

The second profile stops non-Mattermost locations from sending their
unknown-alias service configuration requests to the Mattermost plugin.

To give Mattermost meetings a specific theme (for example one with avatars
enabled), add [`local_policy_mattermost_theme.jinja`](local_policy_mattermost_theme.jinja)
as the profile's local service-configuration policy. It keys on the
`service_tag` the plugin sets and leaves every other service untouched. The
Mattermost **event sink** is configured separately and keeps pointing at
Mattermost directly; it does not go through the proxy.

## Testing the routing

```bash
P=http://localhost      # or https://<proxy>
# 1. proxy itself
curl -s $P/healthz
# 2. service configuration reaches Mattermost (401 without creds proves routing; 200/JSON with them)
curl -s -o /dev/null -w '%{http_code}\n' "$P/policy/v1/service/configuration?local_alias=test&protocol=webrtc"
curl -s -u "$POLICY_USER:$POLICY_PASSWORD" "$P/policy/v1/service/configuration?local_alias=test&protocol=webrtc"
# 3. avatar reaches ad_policy (401 without creds; 200 image / 404 not found with them)
curl -s -o avatar.jpg -w '%{http_code} %{content_type}\n' -u "$POLICY_USER:$POLICY_PASSWORD" \
  "$P/policy/v1/participant/avatar/jsmith?width=100&height=100"
# 4. anything else is 404
curl -s -o /dev/null -w '%{http_code}\n' $P/policy/v1/participant/properties
```

## Running the proxy on Azure App Service (lab)

App Service terminates TLS, so the container runs HTTP-only on port 80.

```bash
az acr build -r $ACR -t ad_policy_proxy:latest proxy/
az webapp create -n ad-policy-proxy -g $RG -p $PLAN \
  --deployment-container-image-name $ACR.azurecr.io/ad_policy_proxy:latest
az webapp config appsettings set -n ad-policy-proxy -g $RG --settings \
  WEBSITES_PORT=80 \
  MATTERMOST_POLICY_URL=https://<mattermost>.azurewebsites.net/plugins/com.pexip.pexip-app/api/ \
  AVATAR_UPSTREAM_URL=https://ad-policy-avatar.azurewebsites.net \
  POLICY_USER=<mattermost plugin user> POLICY_PASSWORD=<mattermost plugin password>
```

Point the Pexip profiles at `https://ad-policy-proxy.azurewebsites.net/`. App
Service does TLS itself, so leave `TLS_MODE` unset (auto → HTTP only inside).
